### 本書の確定と改訂の原則

本書は基本仕様であり、設定形式・採取手段・傾向判定の定数・自然言語テンプレート・MCP入出力スキーマ・軽量性の数値目標を、**規範値（normative）として確定する**。
実装後の実測でこれらの規範値が不適切と判明した場合、詳細設計や実装が値を独自に変えてはならない。**本書（基本仕様）を改訂して反映する**。
これは、上位仕様に対するトレーサビリティを真に保つための原則である。「詳細設計が上位仕様を暗黙に確定・変更する」ことを禁じ、確定値の変更は必ず本書の更新を伴う。

- **2026-08-23（rev.2）**: 詳細設計フェーズのレビューで、凍結済み基本仕様に「実装時に一意解決できない矛盾／技術的に成立しない前提」が見つかったため、要件（要求・要件定義）は維持したまま基本仕様の該当箇所を再オープンし、技術的成立性を確認して再凍結した。変更点は次の3箇所（いずれも「要件をどう実現するか」の手段の修正であり、FR/NFR 自体は不変）。

  - **§7.3–§7.4 Windows GPU 識別**: DXGI/DXCore は PCI バスIDを返さない（LUID のみ）ため、`nvidia-smi`（UUID/PCI）との層間 `StableID` 突合が一致せず同型GPU誤結合の恐れがあった。**ソースを単一化**し、NVIDIA は `nvidia-smi` で完結、DXGI 列挙は NVIDIA を除外（非NVIDIAのみ）することで、層間キー突合そのものを不要にする。あわせて VRAM 使用量は per-process の `QueryVideoMemoryInfo` ではなくシステム全体を表す `GPU Adapter Memory` カウンタから、使用率は全エンジン合算ではなく**最もビジーなエンジンの値**から得る、と手段を正す。

## 1. 本書の位置づけと設計方針

本書は「何を作るか」（要件）を受けて、「どう作るか」の骨格を仕様として定める。
モジュール分割、データモデル、外部インターフェース（MCPツール）、傾向判定と自然言語生成のアルゴリズム、設定ファイル、クロスプラットフォーム戦略、異常系の扱いまでを対象とする。
関数シグネチャや細かなエラーメッセージなど、コードに近い粒度は詳細設計フェーズに残す。

仕様全体を貫く原則を先に置く。

- **自己完結と決定性**：自然言語生成を含め、外部サービスとネットワークに一切依存しない（NFR-3, FR-5）。同じサンプル列からは常に同じレポート文が出る。
- **劣化継続**：取得できない項目は N/A として返し、プロセスは落とさない（FR-7, NFR-5）。GPU非搭載や権限不足を異常ではなく通常の分岐として扱う。
- **軽量性**：常時サンプリングする監視機構そのものが、計測対象の資源を無駄に食わない（NFR-1）。数値目標は §12.1 で規範値として確定する。
- **単一バイナリ**：cgo を使わず `CGO_ENABLED=0` でクロスコンパイルでき、MCPクライアントに STDIO サーバーとして登録するだけで動く（NFR-4, A-2）。

この4原則が、後述の個別判断（GPU取得手段の選定、ロギング先の限定など）の根拠になる。

## 2. システム全体像

### 2.1 実行モデル

本システムは、MCPクライアント（Claude 等）が STDIO で起動する単一プロセスである（FR-1, A-2）。
プロセスは起動と同時に、二つの独立した関心事を並行して動かす。

一つは、**サンプラー**である。
バックグラウンドのゴルーチンが、設定されたサンプリング周期ごとにシステムリソースを測定し、直近ウィンドウ分だけをメモリ上のリングバッファに保持する（FR-2）。

もう一つは、**MCPサーバー**である。
STDIO トランスポート上で JSON-RPC を話し、クライアントからのツール呼び出しに応じてリングバッファの内容を読み、スナップショットまたは傾向レポートを返す。

両者はリングバッファを介してのみ結合する。
サンプラーが書き手、ツールハンドラが読み手であり、この一方向の関係が並行処理の複雑さを最小化する。

### 2.2 データフロー

```
                 [ サンプラー goroutine ]
  周期ごとに測定 ─────────────┐
                              ▼
   OS / gopsutil / GPU     ┌──────────────┐
   採取器 ──────────────▶ │ リングバッファ │ （直近ウィンドウ分のみ）
                          └──────────────┘
                              ▲
                              │ 読み取り（スナップショット複製）
  ┌───────────────────────────┴───────────────┐
  │            MCP サーバー（STDIO）            │
  │  get_current_resources → 現状スナップショット │
  │  get_resource_trend    → 英語の傾向レポート  │
  └───────────────────────────────────────────┘
                    ▲   │
              JSON-RPC │   │ 応答
                    │   ▼
              [ MCP クライアント＝Claude ]
```

STDIO トランスポートでは、標準出力が JSON-RPC 専用の通信路になる。
したがって本システムは、**ログと診断出力を標準エラーだけに書く**。
標準出力への非プロトコル出力はプロトコルを破壊するため、この制約は全モジュールに及ぶ横断的な仕様事項である。

### 2.3 コンポーネント一覧

| コンポーネント | 責務 | 対応要件 |
| --- | --- | --- |
| エントリポイント | 設定読み込み、採取器の初期化、サンプラー起動、MCPサーバー起動、終了処理 | FR-1, FR-6 |
| 設定ローダ | 設定ファイルの探索・解釈・検証。欠如／不正時のデフォルト適用 | FR-6 |
| 採取器（Collector） | CPU／メモリ／GPU の測定。取得不能時の N/A 返却 | FR-3, FR-7 |
| サンプル型（Sample） | 1時点の測定値の集合を表す不変データ | FR-2, FR-3 |
| リングバッファ（Store） | 直近ウィンドウ分のサンプル保持。スレッドセーフ | FR-2 |
| 傾向分析器（Analyzer） | ウィンドウ内サンプル列から系列ごとの傾向を決定的に算出 | FR-4 |
| レポート生成器（Reporter） | 傾向から英語の自然言語文を組み立てる | FR-4, FR-5 |
| MCPサーバー | ツール登録、リクエスト受付、応答整形（構造化出力） | FR-1, FR-3, FR-4 |

## 4. データモデル

### 4.1 サンプル

1回の測定結果を表す不変の値を `Sample` とする。
各数値フィールドは「取得できたか」を表現する必要があるため、取得不能を欠損として持てる形にする（後述 §4.3）。

| フィールド | 型（概念） | 内容 | 取得不能時 |
| --- | --- | --- | --- |
| `Timestamp` | 時刻 | 測定時刻 | 必須（欠損しない） |
| `CPUOverall` | 割合（%） | 全体のCPU使用率 | 欠損 |
| `CPUPerSocket` | 割合の配列 | 物理CPU（ソケット）ごとの使用率 | 空配列 |
| `MemUsedBytes` | バイト | 使用メモリ量 | 欠損 |
| `MemTotalBytes` | バイト | メモリ総容量 | 欠損 |
| `GPUs` | GPUSample の配列 | 搭載GPUごとの測定値 | 空配列（GPU非搭載時） |

`GPUSample` は、GPU 1枚ぶんの測定値を表す。
複数GPU環境（同型GPUの複数枚を含む）で列挙層とメトリクス層を誤って結合しないよう、**安定した識別子の層**を先頭に持たせる（§4.4）。

| フィールド | 型（概念） | 内容 | 取得不能時 |
| --- | --- | --- | --- |
| `StableID` | 文字列 | 起動をまたいで同一GPUを指す安定識別子（`UUID`→`PCIBusID`→`OSAdapterID` の優先で導出） | 必須（何らか） |
| `PCIBusID` | 文字列 | PCI バスID（例 "0000:01:00.0"） | 欠損 |
| `UUID` | 文字列 | ベンダー提供のUUID（NVIDIA 等） | 欠損 |
| `OSAdapterID` | 文字列 | OS のアダプタ識別子（Windows の LUID 等） | 欠損 |
| `Index` | 整数 | **表示用の一時的な列挙番号**（0始まり）。安定識別子ではない | 必須 |
| `Name` | 文字列 | 機種名（例 "NVIDIA GeForce RTX 4090"） | 欠損 |
| `Vendor` | 列挙 | NVIDIA / AMD / Intel / Apple / Unknown | Unknown |
| `UtilPercent` | 割合（%） | GPU使用率 | 欠損 |
| `VRAMUsedBytes` | バイト | VRAM使用量 | 欠損 |
| `VRAMTotalBytes` | バイト | VRAM総容量 | 欠損 |
| `CUDAVersion` | 文字列 | 該当環境のCUDAバージョン | 欠損（非該当時） |

CPU をソケットごとに持つのは、マルチソケット環境への対応要件（FR-3）を満たすためである。
物理CPUが1つの一般的な環境では、`CPUPerSocket` は要素1個の配列になり、`CPUOverall` と一致する。

GPU を配列で持つのは、搭載GPUをすべて列挙し、内蔵GPUも含める要件（FR-3）に対応する。
`Vendor` を分けて持つのは、メトリクス取得手段がベンダーごとに異なるため（後述 §7）と、CUDA の該当可否がベンダーに依存するため（A-5）である。

### 4.2 単位の方針

数値は測定元の生の単位で保持し、表示のための丸めや GB 変換はレポート生成時にだけ行う。
VRAM をバイトで保持し、`get_current_resources` の応答では GB を併記する。
生値を保持することで、傾向判定（§8）が丸め誤差の影響を受けない。

### 4.3 N/A（取得不能）の表現

要件は取得不能項目を「N/A」で返すと定める（FR-3, FR-7）。
機械可読性のため、内部および JSON 応答では**欠損を JSON の `null` で表す**。
すなわち「N/A ≡ `null`」と対応づける。

この対応を採るのは、一次利用者がエージェント（Claude）であり（`hearing.md` §4.1）、文字列 "N/A" より `null` のほうが型を保ったまま判定しやすいからである。
自然言語レポート側では、`null` の項目を "N/A" や "not available" として文章に表す。
`get_current_resources` の `outputSchema`（§6.2）では、各フィールドを nullable として明示する。

### 4.4 GPU 識別子の層（同型GPU誤結合の防止）

GPU の識別を `Index`（列挙順）だけに頼ると、同型GPU複数枚（例 RTX 5090 ×2）の環境で危険がある。
NVIDIA 自身も GPU index の列挙順に一貫性を保証せず、**UUID または PCI バスID による識別を推奨**している。
そこで本仕様は、`GPUSample` に識別子の層（`StableID` / `PCIBusID` / `UUID` / `OSAdapterID`）を持たせ、`Index` は表示用の一時番号と割り切る。

`StableID` は次の優先順で導出する。

1. `UUID` が取れればそれ（最も安定）。
2. なければ `PCIBusID`。
3. なければ `OSAdapterID`（Windows の LUID 等）。
4. いずれも取れない場合のみ、最終手段として `Index + Name` から合成する（不安定である旨を標準エラーに記録）。

この `StableID` は、同一ソース内でGPUを一意に指すための鍵である（§7.3 の**ソース単一化**により、NVIDIA は `nvidia-smi`、非NVIDIA は DXGI と、1つのGPUの全項目が単一ソースから揃う。異種ソース間で同一GPUを突き合わせる必要はない）。
これにより、同型GPUが複数あっても使用率・VRAM を取り違えない。
`StableID` はソースによって導出元が異なる（NVIDIA は UUID/PCIバスID、Windows 非NVIDIA は LUID）。異なるソースの `StableID` を突き合わせないことが、誤結合を防ぐ要点である。

## 5. 設定（FR-6 の確定）

要件は「サンプリング周期とウィンドウ長を設定ファイルで変更でき、欠如／不正時はデフォルト（10秒／60秒）で動く」ことを求める。
形式・場所・キー名は次フェーズ送りだったため（`reqire.md` §9）、本書で確定する。

### 5.1 形式とキー

設定ファイルの形式は **TOML** とする。
TOML を選ぶのは、コメントを書け、階層が浅く、Go の標準的なツール設定で広く使われ、人が手で編集しやすいからである。
JSON はコメントを書けず、YAML はインデント起因の誤りを招きやすい点で、手編集の設定には向かない。

キーは次の2つとする。

```toml
# systemresourcemcp config
sampling_interval_seconds = 10   # サンプリング周期（秒）
window_seconds            = 60   # 傾向を評価するウィンドウ長（秒）
```

### 5.2 探索順

設定ファイルの場所は、次の優先順で解決する。
先に見つかったものを採用し、いずれも無ければデフォルト値で動く。

1. コマンドライン引数 `--config <path>`
2. 環境変数 `SYSTEMRESOURCEMCP_CONFIG`
3. OS標準の設定ディレクトリ（`os.UserConfigDir()` の下 `systemresourcemcp/config.toml`）

OS標準ディレクトリを使うのは、Windows／macOS／Linux それぞれの慣行（`%AppData%`、`~/Library/Application Support`、`~/.config`）に自動で従えるからである。

### 5.3 検証とデフォルト（rev.2）

読み込んだ値は、次の2段階で確定する。

**段階1: 各項目を独立に検証**（満たさなければ該当項目のみデフォルトへ落とし、起動は失敗させない）。

| 項目 | 制約 | デフォルト |
| --- | --- | --- |
| `sampling_interval_seconds` | 1 以上の整数 | 10 |
| `window_seconds` | 1 以上の整数 | 60 |

**段階2: 実効ウィンドウの決定**。段階1で得た値から、
```
実効ウィンドウ = max(window_seconds, sampling_interval_seconds)
```
を採用する。傾向評価には最低1サンプルが必要で、それには実効ウィンドウが周期以上でなければならないためである。

この2段階にした理由は、旧 rev.1 の「`window_seconds` は `sampling_interval_seconds` 以上でなければ不正としてデフォルト(60)へ落とす」という単独条件が矛盾を生んだからである。例えば `sampling_interval_seconds = 120`（合法）で `window_seconds` が未指定/不正なら、フォールバック先の 60 が周期 120 を下回り、条件を満たせないまま確定してしまう。`max` を採ることで、周期をどんな合法値に設定しても常に「実効ウィンドウ ≥ 周期」が成立し、少なくとも1サンプルを保証できる。

`window_seconds`（実効前の値）が周期未満で、実効ウィンドウが引き上げられた場合は、その旨を標準エラーに1行記録する（例: `window raised to 120s to match sampling interval`）。デフォルトへ落としたこと・不正値の内容も同様に記録する（標準出力は使わない。§2.2）。

ファイルが存在しない場合も不正ではなく、単にデフォルト（10秒／60秒、実効ウィンドウ60秒）で動く（FR-6）。
傾向ツールが「充足に必要なサンプル数」を数えるときは、この実効ウィンドウを基準にする（§6.3, §9.3）。

## 6. 外部インターフェース（MCPツール）

要件は公開ツールを2つ（＋任意1つ）と定める（`hearing.md` §8, FR-3, FR-4, FR-8）。
ツール名と入出力スキーマは次フェーズ送りだったため、本書で確定する。

### 6.1 ツール一覧と出力方式

| ツール名 | 目的 | 対応要件 | MVP |
| --- | --- | --- | --- |
| `get_current_resources` | 現状スナップショットを返す | FR-3 | 必須 |
| `get_resource_trend` | 直近ウィンドウの傾向を英語で返す | FR-4 | 必須 |
| `search_processes` | プロセス検索（名前検索／消費上位N） | FR-8 | 任意（将来） |

いずれも入力を取らない設計とする（MVP）。
`get_resource_trend` のウィンドウは設定ファイルで決まるため、呼び出し時の引数は不要である（FR-6）。
将来ウィンドウを呼び出しごとに上書きしたくなった場合に備え、任意引数 `window_seconds` を追加できる余地は残すが、MVP には含めない。

**出力は MCP の構造化出力（structured output）を用いる。**
一次利用者がエージェント（Claude）であり（`hearing.md` §4.1）、機械可読な構造化データが判断に直結するためである。
各ツールは `outputSchema` を宣言し、応答では次の両方を返す。

- `structuredContent`：`outputSchema` に適合する構造化オブジェクト（機械可読の主）。
- `content`：後方互換のための `TextContent`（`structuredContent` を JSON 直列化した文字列。構造化出力に対応しないクライアントでも読める）。

`get_resource_trend` の `content` は、可読性のため JSON ではなく英語レポート本文そのものとし、`structuredContent` に同じレポートとメタ情報を格納する（§6.3）。

### 6.2 `get_current_resources`

入力スキーマは空オブジェクト（引数なし）。
`outputSchema` を `ResourceSnapshot` として宣言し、`structuredContent` に本体を、`content` にその JSON 直列化を後方互換として返す。
取得不能フィールドは `null`（＝N/A）で表す（§4.3）。各フィールドはスキーマ上 nullable として定義する。

### 6.3 `get_resource_trend`

入力スキーマは空オブジェクト（引数なし）。
`outputSchema` を `TrendReport` として宣言する。
`structuredContent` にレポート本文とメタ情報を格納し、`content` には英語レポート本文そのもの（後方互換）を返す。

`TrendReport` の `structuredContent` 例（ウィンドウ充足時）：

```json

  "report": "Over the last 60 seconds:\n- CPU has stayed around 63% steadily.\n- Memory usage is rising, from 40% to 55%.\n- GPU 0 (NVIDIA GeForce RTX 5090) is pinned at 99%.\n- GPU 0 VRAM spiked up to 22.4 GB.",
  "window_seconds": 60,
  "sample_count": 6,
  "data_complete": true
}
```

対応する `content`（TextContent）：

```
Over the last 60 seconds:
- CPU has stayed around 63% steadily.
- Memory usage is rising, from 40% to 55%.
- GPU 0 (NVIDIA GeForce RTX 5090) is pinned at 99%.
- GPU 0 VRAM spiked up to 22.4 GB.
```

起動直後などウィンドウ分のサンプルが未達のときは、集まっている範囲で傾向を返し、`data_complete` を `false` にし、`report` 冒頭で不足を明示する（FR-9）。

データ不足時の `structuredContent` 例：

```json
{
  "report": "Only 2 samples collected so far (need 6 for a full 60s window). Preliminary trend:\n- CPU is around 55% (limited data).",
  "window_seconds": 60,
  "sample_count": 2,
  "data_complete": false
}
```

レポートは英語固定であり（FR-5）、同じサンプル列からは常に同じ `report` 文が出る（§8, §9 で決定性を担保）。

### 6.4 `search_processes`（任意・将来）

MVP 外のため、インターフェースの方向性だけ定める（FR-8）。
実装時は次の2モードを1ツールにまとめ、他ツールと同様に構造化出力（`outputSchema`／`structuredContent`）で返す。

- 名前指定モード：入力 `name`（部分一致）。該当プロセスの CPU／メモリ使用量を返す。
- 上位モード：入力 `top_n`。消費の多い順に上位N件を返す。

いずれのモードも、取得不能項目は `null` で返す。
本ツールはプロセス列挙のコストがサンプリングとは独立に発生するため、常時サンプリングには含めず、呼び出し時にのみ測定する。

## 7. リソース採取（Collector）

`reqire.md` §9 は、各リソースの取得手段（使用ライブラリ、NVML／nvidia-smi／OS API の選定）を次フェーズ送りとした。
本節で確定する。

### 7.1 採取器の抽象

採取器は「測定して `Sample` を1つ返す」役割を持つ。
CPU・メモリ・GPU をそれぞれ独立した採取処理とし、GPU 採取は内部でさらに OS 共通層・ベンダー拡張層へ委譲する。
どの採取処理も、失敗を戻り値（取得不能フラグ）で表し、パニックやプロセス終了に至らせない（FR-7）。

起動時に一度だけ**能力プローブ**を行う。
GPU 列挙手段や `nvidia-smi`／`rocm-smi` の有無、Windows パフォーマンスカウンタの利用可否をこの時点で判定し、以後のサンプリングでは判定済みの手段だけを呼ぶ。
これにより、毎サンプルで存在しないコマンドを試みる無駄を避け、軽量性（NFR-1）に寄与する。

### 7.2 CPU・メモリ

CPU とメモリは、クロスプラットフォームライブラリ **gopsutil**（`github.com/shirou/gopsutil/v4`）で取得する。
gopsutil を選ぶのは、Windows／macOS／Linux を単一APIで扱え、cgo なしで動き（NFR-4）、実績が厚いためである。

CPU 使用率は、直前の測定との差分から算出される性質を持つ。
サンプラーが固定周期で呼ぶため、この差分は自然に周期区間の平均使用率になる。

**マルチソケット対応（FR-3）の手段（rev.2）。**
旧 rev.1 は「論理コア使用率を gopsutil の `PhysicalID` で束ねる」としていたが、これは成立しない。gopsutil の実装では、論理コア別使用率（`cpu.Percent(_, true)`）の要素数と、`cpu.Info()` が返す `InfoStat`（Windows ではソケット/パッケージ単位、macOS では1個で `PhysicalID` 未設定）の要素数・粒度が一致せず、論理コアを `PhysicalID` へ単純対応づけできないためである。
そこで**手段を2つに分離する**。
- **使用率の採取**: gopsutil（`cpu.Percent`）で全体値と論理コア別値を取る。
- **論理コア→物理ソケットのトポロジ対応**: OS 別のトポロジ取得手段を用いる。
  - Windows: `GetLogicalProcessorInformationEx(RelationProcessorPackage)` 等のトポロジAPI（`golang.org/x/sys/windows` 経由、cgo なし）。
  - Linux: `/proc/cpuinfo` の `physical id`（または sysfs）。
  - macOS: `sysctl`（`hw.packages` / `hw.physicalcpu` 等）。

得たトポロジで論理コア使用率をソケットへ束ね、ソケットごとに平均して `CPUPerSocket`（ソケット番号昇順）を作る。
**トポロジが取得できない場合は劣化継続とし、`CPUPerSocket = [CPUOverall]`（要素1個＝全体値）にフォールバックする**（FR-7）。物理CPUが1つの一般的な環境でも同様に1要素になり、全体値と一致する。
この「取れないときは単一要素で全体値」という最小挙動により、FR-3（マルチソケット対応）を満たしつつ、トポロジAPIが使えない環境でもクラッシュしない。

メモリは、使用量と総容量（`MemUsedBytes` / `MemTotalBytes`）を取得する（FR-3）。

### 7.3 GPU の三層戦略（列挙層 → OS共通メトリクス層 → ベンダー拡張層）

GPU は OS とベンダーで取得手段が分かれ、しかも macOS(Apple Silicon) と Linux/NVIDIA は似ていない（`hearing.md` §7）。
要件は Windows／macOS／Linux 正式対応かつ「GPU ベンダー限定なし」で、特に Windows は元要求でも必須である（`reqire.md` §2.1, FR-3）。
この非対称性を吸収し、**特定ベンダーに依存せず OS が提供する共通APIを第一に使う**ため、GPU 採取を次の三層に分ける。

**ソース単一化の原則（rev.2）。**
1つのGPUの全項目（識別子・名前・使用率・VRAM・CUDA）は、**単一のソースから揃える**。異種ソース間で同一GPUを突き合わせる設計は採らない。
理由は、Windows で DXGI/DXCore が PCI バスIDを返さない（得られる識別子は LUID・ベンダーID・デバイスID・VRAM総量・機種名まで）一方、`nvidia-smi` は UUID/PCI を返すため、両者の `StableID` は導出元が異なり突き合わせられないからである。旧 rev.1 は両ソースを `StableID` で突合する前提だったが、キーが一致せず最終手段（index+name）に落ちて同型GPU誤結合を招く。
そこで役割を次のように単一化する。

- **NVIDIA GPU**: `nvidia-smi` だけで完結させる（列挙も使用率もVRAMもCUDAも識別子も、すべて `nvidia-smi` から）。
- **非NVIDIA GPU（AMD/Intel、Windows）**: DXGI 列挙 ＋ PDH メトリクス（§7.4）で完結させる。**DXGI 列挙は NVIDIA（VendorId `0x10DE`）を除外**し、`nvidia-smi` の結果と二重計上しない。
- **Linux / macOS**: 従来どおり（Linux は sysfs 列挙＋NVIDIA=`nvidia-smi`／AMD=`rocm-smi`、macOS は `system_profiler` 列挙のみ）。

**列挙層**は、搭載GPUをすべて数え上げ、機種名・ベンダー・識別子（§4.4）を得る。
使用率や VRAM が取れないベンダー・OS でも、少なくとも「何が挿さっているか」を返せるようにするのが狙いである（FR-3 の「全列挙」「内蔵GPU含む」）。

| OS | 列挙手段 | 得られる識別子 | 備考 |
| --- | --- | --- | --- |
| Windows（非NVIDIA） | DXGI/DXCore（機種名・VRAM総量・LUID・ベンダーID。内蔵GPUも列挙） | `OSAdapterID`(LUID)（PCIバスIDは**取得不可**） | NVIDIA は除外 |
| Windows（NVIDIA） | `nvidia-smi` | `UUID`, `PCIBusID` | 列挙もメトリクスも単一ソース |
| Linux | sysfs（`/sys/class/drm`）＋ PCI ID 解決、補助的に `lspci` | `PCIBusID` | NVIDIA/AMD はベンダー拡張で上乗せ |
| macOS | `system_profiler SPDisplaysDataType -json` | （限定的） | 使用率・VRAM は N/A |

**メトリクス層**（使用率・VRAM）は、ソースごとに次で得る。

| 対象 | 使用率 | VRAM 使用 / 総量 | 手段 |
| --- | --- | --- | --- |
| Windows 非NVIDIA | ○ | ○ | PDH `GPU Engine`（**最ビジーエンジン値**）／VRAM使用は PDH `GPU Adapter Memory` の `Dedicated Usage`（システム全体）、総量は DXGI（§7.4） |
| Windows/Linux NVIDIA | ○ | ○ | `nvidia-smi`（§7.4） |
| AMD（Linux） | △ best-effort | △ | `rocm-smi`（あれば）／sysfs hwmon |
| Intel（Linux） | △ 限定的 | △ | sysfs |
| Apple（macOS） | N/A（原則） | N/A（統合メモリ） | 列挙のみ（§7.4） |

Windows の PDH と DXGI は Windows システムコール（`golang.org/x/sys/windows` 経由）で呼べるため cgo を持ち込まず、単一バイナリ方針（NFR-4）と両立する。

**層間の突き合わせ**は、ソース単一化により**同一ソース内でのみ** `StableID` を鍵に行う（NVIDIA は `nvidia-smi` 内で、非NVIDIA は DXGI 列挙と PDH メトリクスの間で LUID を鍵に）。異種ソースをまたぐ突合は発生しない。
どのソースでも取れない項目は `null`（N/A）のままにする（FR-7）。

### 7.4 NVIDIA・Windows共通層・macOS の具体

**NVIDIA** は、**`nvidia-smi` のサブプロセス呼び出しだけで完結**する（列挙・使用率・VRAM・CUDA・識別子のすべて。rev.2 のソース単一化）。
XML 出力（`nvidia-smi -q -x`）を解釈し、GPU ごとの UUID・PCIバスID・使用率・VRAM使用量・VRAM総量・機種名・CUDAバージョンを一度に得る。
UUID/PCIバスIDが `nvidia-smi` 内で揃うため、識別が安定する（§4.4）。Windows でも NVIDIA はこの単一ソースで扱い、DXGI 列挙からは除外する（二重計上と、LUID↔PCI の橋渡し不能問題を回避）。

NVML（`go-nvml`）ではなく `nvidia-smi` を選ぶのは、単一バイナリ方針（NFR-4）を守るためである。
NVML の直接利用は cgo と共有ライブラリのリンクを要し、`CGO_ENABLED=0` のクロスコンパイルを妨げる。
`nvidia-smi` はドライバに同梱される標準コマンドで、サブプロセス起動だけで済み、cgo を持ち込まない。
周期ごとにプロセスを起動するオーバーヘッドは、既定10秒周期では無視できる水準にあり、軽量性（NFR-1）と両立する。
より低いオーバーヘッドが必要になった場合に備え、NVML 実装をビルドタグで差し替えられる余地は残すが、既定は `nvidia-smi` とする。

**Windows 非NVIDIA 層**（AMD/Intel）は、DXGI 列挙 ＋ PDH メトリクスで使用率・VRAM を取得する（rev.2）。

- **使用率**: PDH の `GPU Engine` カウンタ（`Utilization Percentage`）を用いる。ここで**全エンジンを合算して 100 でクランプしてはならない**。GPU のエンジン（3D / Compute / Copy 等）は並列動作しうるため、3D 60% ＋ Copy 60% を 120%→100% とするのは誤りで、Windows タスクマネージャも「アダプタ全体の代表値＝**最もビジーなエンジンの使用率**」を採る。したがって、同一アダプタ（LUID）について、各物理エンジンごとにプロセス横断で合算し、**エンジン間では最大値を採る**（`adapterUtil = max_engine( sum_process(engineUtil) )`）。
- **VRAM 使用量**: PDH の `GPU Adapter Memory` カウンタの `Dedicated Usage`（**システム全体**のアダプタ専用メモリ使用量）を用いる。DXGI の `IDXGIAdapter3::QueryVideoMemoryInfo().CurrentUsage` は**呼び出しプロセス自身の**video memory 使用量を返すため、監視対象マシン全体の VRAM 使用量にはならない（監視プロセス自身の使用量になってしまう）。したがって VRAM 使用量に `QueryVideoMemoryInfo` は使わない。
- **VRAM 総量**: DXGI の `DedicatedVideoMemory`（アダプタ記述）から得る。

これにより、Windows の AMD・Intel GPU でも使用率と VRAM が返り、要件の「Windows 正式対応・ベンダー限定なし」を満たす。
Windows の NVIDIA GPU はこの層で扱わず、`nvidia-smi` に一本化する（前段落）。

**macOS(Apple Silicon)** の GPU 使用率は、標準では特権を要する手段（`powermetrics` 等）でしか取れない。
特権前提のコマンドを常時叩くのは劣化継続・軽量性の方針に反するため、**macOS の GPU 使用率は既定で N/A** とする。
VRAM は Apple Silicon では統合メモリであり独立した VRAM 概念を持たないため、これも N/A とする。
macOS では機種名の列挙までを保証し、CUDA は常に N/A（A-5）とする。

### 7.5 劣化継続の徹底（FR-7）

各採取処理は、コマンド不在・権限不足・解釈失敗のいずれでも例外を投げず、当該項目を N/A にして戻る。
GPU 列挙が全滅した環境では `GPUs` は空配列になり、他項目（CPU／メモリ）の提供は続く。
失敗の詳細は標準エラーにデバッグレベルで記録し、標準出力には出さない（§2.2）。

## 8. 傾向分析（FR-4 の確定）

`reqire.md` §9 は、傾向判定の閾値とアルゴリズム（「張り付き」「乱高下」「安定」の定義、上昇／下降の判定基準）を次フェーズ送りとした。
本節で決定的アルゴリズムと**規範値としての判定定数**を確定する。

### 8.1 対象系列

傾向分析の入力は、リングバッファ内のサンプル列である。
各サンプルから、次の数値系列を取り出す。

- CPU 全体使用率
- メモリ使用率（`used / total`）
- GPU ごとの使用率
- GPU ごとの VRAM 使用量

GPU 系列は `StableID` で同定し、同型GPU複数枚でも系列を取り違えない（§4.4）。
取得不能で `null` を含む系列は、`null` を除いた実測値だけで評価する。
実測値が0個の系列は、その系列の傾向を出さない（N/A として言及するにとどめる）。

対象を基本項目に限るのは、要件が傾向の対象を基本項目とし、プロセス数などを含めないためである（FR-4, `hearing.md` §5）。

### 8.2 三系統の判定

要件は、傾向レポートが「水準」「変化の向き／変動」「ピーク／張り付き」の3系統を表現できることを求める（FR-4, `hearing.md` §5）。
各系列について、この3系統を独立に判定する。

**水準（レベル）**は、ウィンドウ内の平均値で表す。
変動が小さいときは「安定してその水準」と表現する。

**変化の向き／変動**は、二つの指標で判定する。
向きは、時刻に対する最小二乗回帰の傾きの符号と、区間の正味変化量で決める。
変動の大きさは、変動係数（標準偏差÷平均）と最大最小差で決める。

**ピーク／張り付き（極値）**は、最大値と、高水準がどれだけ持続したかで判定する。
高水準が区間の大半で続けば「張り付き」、単発で大きく跳ねれば「スパイク」とする。

### 8.3 判定定数（規範値）

判定に用いる定数を次のように**規範値として確定する**。
これらは設定ファイルでは変更しない実装内の定数であり（設定で変えられるのは周期とウィンドウのみ。FR-6）、実装上は一箇所（`trend/thresholds.go`）に集約する。
実装後の実測でこれらが不適切と判明した場合は、詳細設計・実装が独自に変えるのではなく、**本書（§8.3）を改訂して反映する**（冒頭「本書の確定と改訂の原則」）。
使用率系（%）は絶対量、VRAM のような量的系列は平均に対する相対量で評価する。

| 判定 | 条件（使用率系, %） | 出力の系統 |
| --- | --- | --- |
| 安定（steady） | 変動係数 < 0.10 | 水準 |
| 乱高下（fluctuating） | 変動係数 ≥ 0.30、または 最大−最小 ≥ 40pt | 変動 |
| 上昇（rising） | 回帰が増加、かつ 正味変化 ≥ 15pt | 向き |
| 下降（falling） | 回帰が減少、かつ 正味変化 ≤ −15pt | 向き |
| 横ばい（flat） | 上記いずれにも当たらない | 向き |
| 張り付き（pinned） | サンプルの90%以上が 95% 以上 | 極値 |
| スパイク（spike） | 最大 ≥ 平均＋2×標準偏差、かつ 最大が高位 | 極値 |

VRAM など量的系列では、「40pt」「15pt」の代わりに平均に対する比率（乱高下: 変動係数 ≥ 0.30、上昇下降: 正味変化 ≥ 平均の25%）を用い、スパイクは同じ統計条件（平均＋2σ）で判定する。
「高位」は、使用率系では 90% 以上を指す。
これらの相対閾値・「高位」の定義も本書の規範値であり、変更は本書の改訂による。

### 8.4 決定性

すべての判定は、入力サンプル列だけから算出される統計量（平均、標準偏差、回帰の傾き、最大最小）に基づく。
乱数も時刻依存の分岐も持たない。
したがって同じサンプル列からは常に同じ判定が出る（FR-5, NFR-3 の決定性）。

## 9. 自然言語生成（FR-5 の確定）

`reqire.md` §9 は、自然言語テンプレートの具体文面を次フェーズ送りとした。
本節で英語テンプレートを確定する。

### 9.1 生成方式

レポートは、§8 の判定結果を英語テンプレートに差し込んで組み立てる（FR-5）。
外部LLMを呼ばず、内部のルールとテンプレートだけで文を作る（FR-5, NFR-3）。
系列ごとに、判定が成立した系統の文を、決まった順序（水準 → 向き／変動 → 極値）で並べる。
成立しない系統の文は出さないため、平穏な系列は短く、特徴のある系列は複数文になる。
組み立てた本文は `TrendReport.report` に入り、メタ情報とともに構造化出力として返る（§6.3）。

### 9.2 テンプレート

系統ごとの英語テンプレートを次のように定める（`{...}` は差し込み値）。

| 系統 / 判定 | テンプレート |
| --- | --- |
| 水準・安定 | `{metric} has stayed around {mean}% steadily.` |
| 水準・一般 | `{metric} is around {mean}%.` |
| 上昇 | `{metric} is rising, from {start}% to {end}%.` |
| 下降 | `{metric} is falling, from {start}% to {end}%.` |
| 乱高下 | `{metric} is fluctuating widely (between {min}% and {max}%).` |
| 張り付き | `{metric} is pinned at {max}%.` |
| スパイク（%） | `{metric} spiked up to {max}%.` |
| スパイク（VRAM 等） | `{metric} spiked up to {max_gb} GB.` |

`{metric}` は、系列に応じて `CPU`、`Memory usage`、`GPU {index} ({name})`、`GPU {index} VRAM` のように具体化する。
表示では `{index}` を使うが、これは §4.4 の表示用番号であり、内部の系列同定は `StableID` で行う（表示番号が入れ替わっても取り違えない）。
GPU が複数枚あるときは、枚ごとに `GPU 0 ...`、`GPU 1 ...` と列挙し、どのGPUの話かを一意にする。

### 9.3 データ不足時（FR-9）

ウィンドウ分のサンプルが未達のときは、集めた範囲で判定し、先頭に不足を明示する一文を置き、`TrendReport.data_complete` を `false` にする（§6.3 の例）。
サンプルが1個以下で傾向を出せない系列は、水準のみ「limited data」を添えて述べるか、言及を省く。
この分岐により、起動直後の呼び出しでもエラーで落ちず、限定的データに基づく応答と不足の明示が返る（FR-9）。

## 10. 並行処理とライフサイクル

### 10.1 起動

エントリポイントは次の順に配線する。

1. コマンドライン引数と設定を読み、周期・ウィンドウを確定する（§5）。
2. 採取器を初期化し、能力プローブを一度実行する（§7.1）。
3. リングバッファを、ウィンドウ長÷周期に若干の余裕を足したサイズで確保する。
4. 起動直後に1サンプル採取し、スナップショットが即座に空にならないようにする。
5. サンプラーのゴルーチンを起動する（周期ごとのティッカー）。
6. MCPサーバーを STDIO で開始し、ブロッキングでリクエストを待つ。

### 10.2 サンプラー

サンプラーは、周期ごとに採取器を呼び、得た `Sample` をリングバッファへ追加する。
バッファはウィンドウを超えた古いサンプルを捨てる（FR-2）。
履歴の永続化は行わない（FR-2, A-3）。

### 10.3 排他制御

リングバッファは、サンプラー（書き手）とツールハンドラ（読み手）から並行アクセスされる。
ミューテックスで保護し、ツールハンドラは読み取り時にサンプル列のスナップショットを複製してからロックを解放する。
複製後は分析・文生成をロック外で行い、サンプリングを妨げない。
この設計は、監視自体を軽く保つ方針（NFR-1）と、応答生成中もサンプリングを止めない要請に沿う。

### 10.4 終了

標準入力の EOF（クライアント切断）または終了シグナルを受けたら、サンプラーを止め、プロセスを正常終了する。
永続化する状態が無いため、終了処理は資源の解放のみで足りる。

## 11. 異常系とロギング

すべての採取失敗は、当該項目の N/A 化で吸収し、プロセスを落とさない（FR-7, NFR-5）。
想定する失敗と扱いを次に示す。

| 事象 | 扱い |
| --- | --- |
| GPU非搭載 | `GPUs` 空配列。CPU／メモリは通常どおり |
| `nvidia-smi` 不在 | NVIDIA ベンダー拡張を N/A。Windowsでは共通層で使用率・VRAM を取得、他OSでは列挙層で機種名のみ |
| Windows パフォーマンスカウンタ利用不可 | 使用率・VRAM を N/A、列挙層で機種名のみ |
| 権限不足 | 取得できた項目のみ返し、不能項目は N/A |
| 同型GPUで安定識別子が取れない | index+name で突合し、不安定である旨を標準エラーに記録 |
| 設定ファイル不正 | 該当項目をデフォルトに落として起動継続（§5.3） |
| 採取コマンドの解釈失敗 | 当該項目 N/A、標準エラーにデバッグ記録 |

ログは標準エラーにのみ出力する（§2.2）。
標準出力は MCP の JSON-RPC 専用であり、ここへ非プロトコル出力を混ぜるとクライアントとの通信が壊れるためである。

## 12. 非機能設計

### 12.1 軽量性の数値目標（NFR-1 の確定・規範値）

`reqire.md` §9 は NFR-1 の具体数値目標を次フェーズ送りとしていたが、本書で**規範値として確定する**。
数値は既定設定（周期10秒・ウィンドウ60秒＝6サンプル）・アイドル環境を前提とする。

| 指標 | 規範値 |
| --- | --- |
| 監視プロセスの平常時CPU使用率 | 1論理コア換算で **1% 未満**（サンプリング間隔の平均） |
| 瞬間ピークCPU使用率（GPU採取のサブプロセス起動を含む） | 1論理コア換算で **5% 未満** |
| 常駐メモリ（RSS）増分 | **50 MB 未満** |
| メモリ増分の増え方 | サンプル数 `ceil(window/interval)` に対して線形（1サンプルあたり数KB規模、GPU枚数に比例） |

検証方法は、アイドル環境で監視プロセス自身の CPU 時間と RSS を既定設定のまま一定時間（目安5分）計測し、上記を満たすことを確認する（§13 に計測テストを置く）。
実測でこの規範値を満たせない／過大と判明した場合は、本書（§12.1）を改訂する。

### 12.2 その他の非機能対応

| 要件 | 仕様上の対応 |
| --- | --- |
| NFR-1 軽量性 | 既定10秒周期の低頻度サンプリング。分析はロック外。GPU は起動時プローブ済み手段のみ呼ぶ。数値目標は §12.1 |
| NFR-2 クロスプラットフォーム | CPU／メモリは gopsutil で共通化。GPU は列挙層＋OS共通メトリクス層＋ベンダー拡張層で吸収し、同一ツール仕様のまま OS 差を N/A で埋める |
| NFR-3 決定性・自己完結 | 分析と文生成は統計量とテンプレートのみ。ネットワーク非依存。同一入力に一意出力 |
| NFR-4 配布容易性 | `CGO_ENABLED=0` の純Go単一バイナリ。GPU はサブプロセス呼び出し／Windowsシステムコールで cgo を避ける。STDIO 登録のみで起動 |
| NFR-5 堅牢性 | 全採取失敗を N/A 化で吸収し異常終了しない（§11） |

## 13. テスト方針

決定性（FR-5）が本システムの検証の中心になるため、傾向分析と文生成を最優先でテストする。

- **傾向分析・文生成**：固定のサンプル列を入力に、期待する英語文が一意に出ることをテーブル駆動で検証する。3系統（水準／変化／極値）それぞれの成立・不成立、データ不足時の分岐を網羅する。
- **構造化出力**：`get_current_resources`／`get_resource_trend` の応答が `outputSchema`（`ResourceSnapshot`／`TrendReport`）に適合し、`structuredContent` と後方互換 `content` が整合することを検証する。
- **GPU 識別子突合**：同型GPU複数枚を模した列挙層・メトリクス層の入力に対し、`StableID` により正しく結合されること、安定識別子欠如時に index+name へフォールバックすることを検証する。
- **設定ローダ**：ファイル欠如、不正値、境界値（ウィンドウ＜周期）でデフォルトに落ちることを検証する。
- **GPU 解釈**：`nvidia-smi -q -x` の XML、`system_profiler` の JSON、Windows カウンタ／DXGI の取得結果など、実環境で採取した出力をゴールデンファイルとして固定し、解釈結果を検証する。これによりGPU実機なしでも解釈ロジックを回帰テストできる。
- **劣化継続**：採取器が失敗を返す模擬環境で、スナップショットが N/A を含みつつ他項目を返し、プロセスが落ちないことを検証する。
- **軽量性（NFR-1）**：アイドル環境で監視プロセスの CPU／RSS を既定設定のまま計測し、§12.1 の規範値を満たすことを確認する。

本書で仕様（骨格と規範値）は固めた。
