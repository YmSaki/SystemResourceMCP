> このドキュメントは、要件定義に先立って行った対話で拾い上げた**生の要求（Wants）**と、その背景・動機・やりとりの記録である。
> ここに書かれているのは「システムが満たすべき条件」に翻訳する**前**の素材であり、検証可能な要件は `reqire.md` にまとめる。

---

## 1. 用語の合意（この対話の前提）

対話冒頭で、以下3語を区別することに合意した。

- **要求（Request / Wants）**: 「こうしたい」「こうなってほしい」という主観的な望み。背景・動機・困りごとを含む、未整理の生の声。
- **要件（Requirement）**: 要求を「システムが備えるべき条件」に翻訳したもの。検証可能で、機能／非機能に分けられる。
- **要件定義（Requirements Definition）**: 要求を引き出し・整理し、過不足なく・矛盾なく・検証可能な形に落とす行為とその成果物。優先順位付け・スコープの線引き・前提／制約の明文化を含む。

ヒアリングの方針: 要求を即座に要件へ変換せず、まず「なぜそれが欲しいのか」を掘る。要求が要件の体裁で語られたときも、いったん要求へ引き戻して背景を確認する。

## 4. 背景・動機（「なぜ」の深掘り）

### 4.1 解決したい困りごと（一次動機）
> 「今CPUに空きがあり、そっちで回せるか、GPUにどれだけの余裕があるのか分かってもらえず、計算資源を無駄にしていた。」

- **計算資源の遊びを無くしたい**、というのが核心。
- 「分かってもらえず」の主体は **AIエージェント**。具体的には「**Claude に実験を任せたとき**にそうなった」。
  - つまり本 MCP の一次利用者（読者）は**人間ではなく、実験を回す Claude エージェント**。エージェントが「今この処理を投げてよいか／並列化してよいか／GPUを使ってよいか」を判断する材料が無かった。

### 4.2 「自然言語で報告」の狙い
- 自然言語化の**主体は MCP サーバー自身**。「MCPが特徴パターンをもとに機械的に自然言語として返却する。LLMを介す必要はない。」
- つまり **決定的（ルール／パターンベース）** で、外部LLMに依存しない。
- 目的は、エージェントが即座に解釈できる形にすること（数値の羅列より、傾向の言語化が判断に効く）。

### 4.3 「報告」の駆動モデル
- 「『直近60秒の傾向』を自然言語で返せばいい。」
- 能動プッシュではなく、**プル型**（クライアントが尋ねたら返す）で足りる、と確認。
- 内部では常時サンプリングしておき、問い合わせ時に直近ウィンドウの傾向を返す形。

## 5. 傾向として表現したい内容（依頼者の具体例）

「直近60秒の傾向」で伝わってほしい情報を、依頼者が具体例で示した。

> 「プロセスが増えたり減ったりしてる、メモリは乱高下してる、ずっと7割で安定している、VRAMが17GBまで跳ね上がった、常時99%張り付き、こんな感じ。」

ここから、傾向レポートが表現すべき系統は3つと整理した。

1. **水準（レベル）**: 例「7割で安定」。平均的にどれくらいか。
2. **変化の向き／変動**: 例「メモリが乱高下」「プロセスが増減」。上昇・下降・横ばい・乱高下。
3. **ピーク／張り付き（極値）**: 例「VRAMが17GBまで跳ね上がった」「常時99%張り付き」。

## 6. GPU / CPU まわりの方針（回答の記録）

- **GPU はあるものを出すだけ**。「GPUがあればそれを出すというだけです。オンボード含みます。」
  - ベンダー限定なし（NVIDIA に限らない）。**内蔵GPU（オンボード）も対象**。
  - 複数枚あれば「**全部列挙**」。
- **CPU が複数（マルチソケット）あればそれも対応**。「CPUが2つあるならそれも対応。」
- **CUDA は該当する環境だけ**。「Radeon も CUDA はなしでいい。」Mac・AMD・非該当環境では **N/A** で出してよい。「該当なしで出していい。」

---

## 7. スコープ（対象OS）

- Windows: **必須**（依頼者が使用）。
- Mac: 対応したい。「Windowsを使っているのでWindowsがあればいいが、友人はMac使いなので、Mac対応してあげたいなと。」
- Linux について、依頼者から質問があった。
  > 「Mac対応するとリナも大体対応するんじゃないの？」
  - これに対して回答（記録）: **半分正しく半分違う**。CPU/メモリ/プロセス等の基本項目はクロスプラットフォームライブラリ（gopsutil 等）で Windows/Mac/Linux 一括で取れる。ただし **GPU は OS ごとに実装が分かれる**。しかも macOS(Apple Silicon) と Linux は似ておらず、**Linux の NVIDIA は Windows と同じ NVML/nvidia-smi 系**に近い。したがって Mac 対応が Linux 対応を自動的にもたらすわけではないが、Linux を正式対象に加える追加コストは比較的低い。
  - 依頼者の決定: **Windows / Mac / Linux の3つを正式対応**（3択のうち b を選択）。

## 8. その他の確定事項（回答の記録）

- **公開ツールは2つ**（＋任意1つ）。
  - 「現在の状況を知るツールと、直近60秒の傾向がどうだったか把握できるツールの2つがあればいい。」
- **取得項目は基本項目のみ**。「基本項目のみ。」（追加項目：コア数・ディスク・ネットワーク・温度・スワップ 等は**入れない**と回答。）
- **出力言語は英語固定**。「言語は英語デフォルト。その他言語は対応なし。」
- **サンプリング周期・ウィンドウは設定ファイルで変更可**。「設定ファイルでサンプリング周期とウィンドウを変えれていい。」
- **プロセス数は任意項目**。「プロセスは任意。指定なし。」
- **プロセス検索は「あったら嬉しい枠」**。イメージは「名前で検索」＋「消費上位N」の両方（c を選択）だが、優先度は低く MVP 外。「なくてもいい。あったら嬉しい枠。」

## 9. 依頼者が明言していない前提（合意済み）

以下は依頼者が明言していないが、要件化に必要なため私（Claude）が補い、依頼者が「OK」と承認した前提。

1. **実行形態**: Go の単一バイナリ。MCP クライアント（Claude 等）に STDIO で登録して起動される。
2. **内部動作**: 起動中は常時バックグラウンドでサンプリングし、直近ウィンドウ分のみメモリ保持（リングバッファ）。**履歴の永続化はしない**。プル型で問い合わせ時に集計。
3. **設定ファイル**: サンプリング周期・ウィンドウを変更可能。欠如／不正値時はデフォルト（10秒／60秒）で動作。ファイル形式は仕様フェーズで決定。
4. **傾向の言語化**: ルール／パターンベースで決定的、英語固定、LLM非依存。表現系統は「水準・変化の向き・ピーク／張り付き」。
5. **堅牢性**: 取得できない項目はクラッシュせず N/A を返して継続（graceful degradation）。監視自体は軽量に保つ。
6. **起動直後**: ウィンドウ分のデータが未達のときは、集まっている範囲で傾向を返し、データ不足である旨を示す。
7. **項目の網羅**: 基本項目のみ。複数GPU全列挙・内蔵GPU含む・マルチソケットCPU対応。CUDAは非該当環境で N/A。
