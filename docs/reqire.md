## 1. 目的・背景（サマリ）

AIエージェント（特にローカルで実験を回す Claude）が、**計算資源の空き状況を把握できず、CPUに余裕があるのに使わない・GPUの余裕を判断できず、計算資源を遊ばせてしまう**という無駄を解消する。

そのため本システムは、実行中マシンのシステムリソースを **STDIO トランスポートの MCP サーバー**として公開し、エージェントが「今この処理を投げてよいか／並列化やGPU利用をしてよいか」を判断できる材料を提供する。判断材料は、(1) 現在の状況スナップショットと、(2) 直近ウィンドウの傾向を**決定的に生成した英語の自然言語レポート**の2形態で提供する。

---

## 2. スコープ

### 2.1 対象（In Scope）
- 対象OS: **Windows / macOS / Linux** の3プラットフォームを正式対応とする。
- リソース取得（現状スナップショット）。
- 直近ウィンドウ（既定60秒）の傾向の自然言語レポート。
- 設定ファイルによるサンプリング周期・ウィンドウの変更。

### 2.2 対象外（Out of Scope）
- 履歴の永続化（ファイル・DBへの保存）。本システムはメモリ内の直近ウィンドウのみを扱う。
- 能動プッシュ／定期通知（プル型のみ。クライアントが尋ねたときに返す）。
- 英語以外の出力言語。
- 基本項目以外のリソース（CPUコア数・ディスク・ネットワーク・温度・スワップ 等）。
- 外部LLMの呼び出し（自然言語化は内部のルール／パターンで完結する）。

### 2.3 任意・将来対応（Optional / Nice-to-have、MVP外）
- **プロセス検索機能**（優先度低）。詳細は FR-8 を参照。

## 3. 用語

| 用語 | 定義 |
| --- | --- |
| 現状スナップショット | ある瞬間のリソース測定値の集合。 |
| サンプリング周期 | リソースを測定する時間間隔。既定 10 秒。 |
| ウィンドウ | 傾向を評価する対象期間。既定 60 秒（＝既定では直近6サンプル相当）。 |
| 傾向レポート | ウィンドウ内のサンプル列から決定的に生成した英語の自然言語文。 |
| N/A | その環境・権限では取得できない項目を表す値。 |

## 4. 機能要件（Functional Requirements）

### FR-1. STDIO MCP サーバーとして動作する
- 本システムは MCP サーバーであり、**STDIO トランスポート**で MCP クライアント（Claude 等）と通信する。
- 検証: MCP クライアントに STDIO サーバーとして登録でき、ツール一覧・呼び出しが成立する。

### FR-2. リソースの継続サンプリング（内部動作）
- サーバー起動中、**サンプリング周期ごと**にシステムリソースを測定し、**直近ウィンドウ分のサンプルのみ**をメモリ上に保持する（リングバッファ相当）。
- 履歴の永続化は行わない。
- 検証: 起動後、周期ごとに内部サンプルが更新され、ウィンドウを超える古いサンプルは破棄される。

### FR-3. 現状スナップショット取得ツール
- クライアントの要求に応じて、**現在のリソース状況**を返すツールを提供する。
- 返す基本項目（取得可能なもの）:
  - CPU 使用率（物理CPUが複数＝マルチソケットの場合はそれも扱えること）
  - メモリ使用率、メモリ最大量（総容量）
  - GPU 使用率
  - VRAM 使用量、VRAM 最大サイズ
  - GPU 種類（機種・名称）
  - CUDA バージョン
- **GPU は搭載されているものをすべて列挙**する（複数枚対応）。**内蔵GPU（オンボード）も含む**。ベンダーは限定しない。
- 取得できない項目は **N/A** として返し、処理を継続する（FR-7 参照）。
- 検証: GPUなし環境／複数GPU環境／マルチソケット環境それぞれで、取得可能な項目が返り、不能な項目は N/A になる。

### FR-4. 傾向レポート取得ツール（直近ウィンドウ）
- クライアントの要求に応じて、**直近ウィンドウ（既定60秒）の傾向**を**英語の自然言語**で返すツールを提供する。
- レポートは以下3系統を表現できること:
  1. **水準（レベル）**: 例 "CPU has stayed around 70% steadily."
  2. **変化の向き／変動**: 例 "Memory usage is fluctuating widely." / 上昇・下降・横ばい・乱高下。
  3. **ピーク／張り付き（極値）**: 例 "VRAM spiked up to 17 GB." / "GPU is pinned at 99%."
- 対象は基本項目（CPU・メモリ・GPU使用率・VRAM 等）。
- 検証: ウィンドウ内のサンプル列に対し、同じ入力から同じ文が生成される（決定的）こと、上記3系統が表現できること。

### FR-5. 自然言語生成は決定的・LLM非依存
- 傾向レポートの文面は、**内部のルール／パターン**により機械的に生成する。
- **外部LLMを呼び出さない**。APIキー等の外部依存を持たない。
- 出力言語は **英語固定**。
- 検証: ネットワーク遮断状態でも傾向レポートが生成できる。同一入力に対し出力が一意。

### FR-6. 設定ファイルによる周期・ウィンドウの変更
- **サンプリング周期**と**ウィンドウ長**を設定ファイルで変更できる。
- 設定ファイルが**無い／値が不正**な場合は、既定値（サンプリング周期 10 秒、ウィンドウ 60 秒）で動作する。
- 検証: 設定を変更するとサンプリング周期・ウィンドウが反映される。設定欠如／不正時は既定値で正常起動する。

### FR-7. 取得不能時の劣化継続（graceful degradation）
- GPU非搭載・権限不足・非対応環境などで一部項目が取得できない場合でも、**クラッシュせず** N/A を返して他項目の提供を継続する。
- 検証: GPUドライバ不在／権限不足を模した環境でサーバーが落ちず、取得可能な項目は返る。

### FR-7.1. 取得手段が無い場合の N/A 許容（契約、2026-08-23 追加）
- ある項目・対象を取得できる**手段（ツール／API／コマンド）がその環境に存在しない場合、その項目・対象を取得しないこと（N/A）を許容する。取得手段が無いこと自体は欠陥ではない。**
- ただし、取得できる手段が**一つでも存在するなら、その手段で取れる範囲は取得する**（「手段があるのに取らない」は不可）。
- FR-3 の「搭載GPUをすべて列挙」も、**利用可能な手段で列挙・取得できる範囲**に限る。ある項目を出す手段が無ければ、その項目のみ N/A でよく、他の手段で取れる項目（例: 使用率・VRAM は取れるが CUDA は取れない）は取得する。
- 背景・意図: `hearing.md §3 R-5`。判断材料が「取れる範囲で取れていれば足りる」という要求（`hearing.md §6`「GPUがあればそれを出すだけ」）の一般化。
- 検証: ある取得手段（例: `nvidia-smi`）が不在の環境で、当該手段でしか取れない項目（例: CUDAバージョン）は N/A になり、他手段で取れる項目（例: OS共通APIによる使用率・VRAM）は返る。手段が皆無の項目が N/A でもサーバーは正常。

### FR-8.（任意・優先度低）プロセス検索
> MVP外。要件としては「あったら嬉しい枠」で記録する。実装可否・時期は将来判断。
- (a) **名前でプロセスを検索**し、その CPU／メモリ使用量を返す。
- (b) **リソース消費の多い順に上位N件**のプロセスを一覧で返す。
- (a)(b) 両方を対象イメージとする。
- 検証（実装時）: 指定名のプロセスの使用量が返る／上位N件が消費順で返る。

### FR-9. 起動直後（ウィンドウ未充足時）の挙動
- 起動直後などウィンドウ分のサンプルが未達のときは、**集まっている範囲で傾向を返し、データが不足している旨を示す**。
- 検証: 起動直後に傾向ツールを呼んでもエラーで落ちず、限定的データに基づく応答＋不足の明示が返る。

## 5. 非機能要件（Non-Functional Requirements）

### NFR-1. 軽量性（オーバーヘッド）
- 常時サンプリングを行う監視機構自体が、計測対象のリソースを過度に消費してはならない（無駄を無くす目的に反するため）。
- 目安: 監視による CPU／メモリ使用は無視できる水準に保つ（具体的な数値目標は仕様フェーズで設定）。

### NFR-2. クロスプラットフォーム
- Windows / macOS / Linux の3つで動作する。
- OSごとに取得可能な項目差（例: macOS には CUDA が無い）は N/A で吸収し、同一のツール仕様で動作する。

### NFR-3. 決定性・自己完結
- 自然言語生成を含め、外部サービス・ネットワークに依存せずローカルで完結する。

### NFR-4. 配布・実行容易性
- Go の単一バイナリとして配布・実行でき、MCP クライアントへ STDIO サーバーとして登録するだけで使えること。

### NFR-5. 堅牢性
- 想定外の環境（GPUなし、権限不足、ドライバ不在等）でもプロセスが異常終了しない（FR-7 と対応）。

## 6. 前提・制約（Assumptions & Constraints）

- **A-1**: 実装言語は Go（既存リポジトリが Go 構成）。
- **A-2**: 実行形態は単一バイナリ、MCP クライアントから STDIO で起動される。
- **A-3**: データはメモリ内の直近ウィンドウのみ。永続化しない。
- **A-4**: 設定ファイルの形式・場所・キー名は仕様フェーズで決定（本書では「変更可能」であることのみを要件とする）。
- **A-5**: CUDA は NVIDIA 環境のみ該当。AMD(Radeon)・macOS・非該当環境では N/A。
- **A-6**: GPU の取得手段は OS／ベンダーごとに異なりうる（macOS は Windows/Linux と実装が分かれる）。手段の選定は仕様フェーズ。

## 8. 受け入れ基準（Acceptance Criteria の要点）

本要件を満たすと判断するための最小条件:

1. Windows / macOS / Linux のいずれでも、STDIO MCP サーバーとして起動・登録できる。
2. 現状スナップショットツールが、その環境で取得可能な基本項目を返し、不能項目は N/A になる（複数GPU全列挙・内蔵GPU含む・マルチソケット対応）。
3. 傾向ツールが、直近ウィンドウのサンプルから「水準・変化・ピーク／張り付き」を英語で決定的に表現する。
4. 設定ファイルで周期・ウィンドウを変更でき、欠如／不正時は 10 秒／60 秒で動作する。
5. GPU非搭載・権限不足環境でもクラッシュしない。
6. 外部LLM・ネットワークに依存せず傾向レポートを生成できる。

## 9. 次フェーズ（基本仕様定義）への申し送り

要件段階では確定させず、仕様フェーズで決める事項:

- 設定ファイルの形式・場所・キー名・既定パス。
- 各リソースの取得手段（使用ライブラリ、NVML/nvidia-smi/OS API 等）の選定。
- 傾向判定の閾値・アルゴリズム（「張り付き」「乱高下」「安定」の定義、上昇/下降の判定基準）。
- MCP ツールの名称・入出力スキーマ（引数・レスポンス構造）。
- 自然言語テンプレートの具体文面。
- NFR-1 の軽量性の具体数値目標。
